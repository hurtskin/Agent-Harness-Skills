# 核心工作区文档流程

> 仅在用户选择“核心工作区文档”时加载。

## 1. 项目识别

并行读取仓库结构、项目清单、README、入口、测试配置和已有 Agent 规则。确认：

- 项目名称、类型和目标
- scope 与 non-goals
- 用户角色、工作语言和部署形态
- 协作模式：单人 / 多人协同（证据：git log 多作者、组织 remote、团队 README 说明；无证据或证据冲突时必须询问“是否多人协同工作”，不猜测）
- 多人协同时确认成员名单与当前用户标识：当前用户优先从 `git config user.name` 推断；无证据或证据冲突时询问一次并登记，后续会话不再重复
- 当前任务、活跃 Spec 和项目红线

有可靠证据则推断；否则结构化询问，不猜多问。

## 2. 核心产物

按顺序生成或升级：

1. `AGENTS.md`：P0 唯一常驻事实源，包含短导航、协作原则、安全红线与踩坑教训；所有 Agent Harness 都原生加载该文件，换工具零迁移。
2. `decisions/`：P2 决策目录，一决策一文件 + `_INDEX.md` 索引（第 5 节）。
3. Claude Code 适配器要求的薄入口。
4. 多人协同模式额外产物：`.agents/<当前成员>/` 个人层骨架与 `.gitignore` 忽略条目（第 6 节）。

不生成独立的 `soul.md` 或 `lessons-learned.md`：协作原则与教训直接作为 `AGENTS.md` 的章节维护，通过顶部锚点目录跳转定位。旧体系项目按第 10 节迁移。

排期清单、verify-matrix、drift-inventory 不属于本流程；只有用户选择对应模块时才加载和生成。

## 3. 协作原则与红线章节

协作原则、红线两个独立章节，只保留跨多数任务稳定成立、缺失会导致错误执行的原则；项目身份、scope / non-goals、协作语言放在“项目定位”章节，不重复进原则清单。

协作原则章节常规条目：

- 不猜多问、先对齐后行动、最小改动
- 文档先于代码与 Spec 唯一事实源
- 专用工具优先于终端命令；终端仅用于 Git、依赖、构建和测试
- Bug 先报告、确认后修复
- 每次会话从 `AGENTS.md` 获取当前入口；P1 仅在任务命中时读取，P2 先读 `decisions/_INDEX.md` 按关键词定位，再读对应决策文件

红线章节常规条目：

- Git：不改配置；未经明确要求不 commit/push；禁止擅自 force push、硬重置、清理或覆盖已有改动
- 依赖：先核对项目清单；未经确认不新增、升级或全局安装依赖
- 删除：删除文件、迁移脚本或破坏性数据操作必须先确认并说明影响
- 临时文件：统一 `temp_*` 前缀命名，使用后立即删除；不得提交缓存、日志、密钥

不得在原则或红线中堆放当前任务、详细架构、命令大全、决策历史正文或客户端重复规则。工具规则必须条件化：决策检索固定走 `decisions/_INDEX.md` 关键词定位；未安装 verify-matrix / drift-inventory 时，使用项目现有测试/检查命令，不写不存在的强制命令。

## 4. AGENTS.md 整体结构

AGENTS 是 P0 唯一事实源，不是项目知识全文。按以下章节顺序生成，顶部目录锚点链接到各章节，解决单文件可维护性：

1. **标题 + 目录**：锚点列表，链接到下列各章节。
2. **项目定位**：一句话定位；Scope、Non-goals、协作语言、协作模式四个要点（协作模式为“单人”或“多人协同”；多人协同时列出成员名单，成员以 git user.name 标识）。
3. **当前入口**：入口表（入口 + 用途），覆盖 README、各 Skill 入口、排期清单等；附一句活跃 Spec 状态说明。
4. **真实验证命令**：从仓库根分块给出真实可运行命令；若安装了 Spec 工具，按「Spec 工具（可选）」表列出 verify / drift 入口（解释器由项目指定，不写死 uv）。
5. **协作原则**：第 3 节定义的条目。
6. **红线**：第 3 节定义的条目。
7. **多人协作**（仅多人协同模式生成）：三层规则摘要、个人层路径、晋升流程与序号认领规则（第 6 节）。
8. **踩坑教训**：第 7 节定义的格式；初始为空时保留规范说明和「（暂无条目）」。
9. **Spec 工具（可选）**：按所选 bootstrap 模块填写 `templates/agents/SPEC_TOOLS.md.snippet`（启用列 yes/no + 探测路径）；未装工具填 no。用法不在 AGENTS 展开，指向 spec-writing。
10. **P1 / P2 索引**：一张表（级别 + 路径 + 读取条件）；P1 覆盖 README、Skill 文档、CI 配置、排期清单、`specs/`（按第 8 节层级约定）等，P2 覆盖 `decisions/`（入口是 `_INDEX.md`）、归档 Spec。
11. **文档职责**：每个事实源一行，写清各自承载什么、不承载什么。
12. **Agent 工具适配**：表（工具 + 自动加载入口 + 状态 + 来源 + 最后确认日期）；未确认的入口标记 `pending-confirmation`。
13. **AGENTS.md 变更日志**（可选，决策 v21）：人类时间线展示；只挂结构级变化（章节增删 / 协作原则改写 / 模板验收清单改写 / v* 决策落地）；过程性条目（修脚本 / 加注释 / 删错别字）走 `decisions/_INDEX.md` 而非变更日志。模板仍保留「章节结构完整」描述以便装到消费者项目时按需启用。

单人模式不生成第 7 项「多人协作」章节，目录锚点随之省略。未选 Spec 工具模块时不生成第 9 项或保留表且全部 `no`。

详细架构与数据流正文应留在对应 Spec/架构文档；历史任务和完整决策不得回填到 AGENTS。

## 5. decisions/ 决策目录规范

决策记录采用一决策一文件的目录结构，文件系统即索引：

```text
decisions/
├── _INDEX.md                          ← 唯一索引表
├── 001-v0.1-init-project.md
├── 002-v0.2-repo-limit-ts.md
└── ...
```

- **文件命名**：`序号-版本-关键词1-关键词2.md`。序号三位递增；版本是决策发生时的项目版本，无版本化项目可省略；关键词用小写英文 kebab-case，选能命中未来查询的词（技术选型、模块名、行为关键词）。
- **序号认领**：序号在晋升时刻（决策写入 `decisions/` 时）分配——读当前 `_INDEX.md` 取最大序号 +1，序号与版本号一一对应（014 ↔ v14），改号时两处同步。草稿阶段（多人协同的个人层）不使用序号和版本号，避免固化后重命名的连锁成本。
- **决策文件内容**：标题（`vN · 主题（日期）`）+ 元数据（状态 / 关键词 / 相关模块；多人协同模式必填第四行「作者」）+ 关联文档、变化程度、摘要。
- **_INDEX.md**：唯一索引表（文件 | 版本 | 关键词 | 状态 | 相关模块）；多人协同模式增加「作者」列。新增决策后必须追加一行，否则决策不可发现。
- **状态规则**：默认活跃；被后继决策修正或推翻时改为「归档（见 后继序号）」，旧文件保留，正文不改写。
- **新增决策**：决策闭环后新建文件 + `_INDEX.md` 追加一行；多人协同按第 6 节晋升流程执行。
- **初始化行为**：创建 `decisions/_INDEX.md` + 首条决策 `001-v1-init-<项目关键词>.md` 记录本次初始化。
- **检索路径（写入 AGENTS.md 协作原则）**：追溯决策时先读 `_INDEX.md` 按关键词定位，再读对应决策文件；`ls decisions/` 可直接浏览全史；不整目录预读。

## 6. 多人协同模式

仅协作模式为“多人协同”时执行本节；单人模式跳过（产物、章节、gitignore 条目均不生成）。

### 6.1 三层结构

```text
project/
├── AGENTS.md                 # 宪法层：Git 跟踪
├── BACKLOG.md                # 宪法层：Git 跟踪
├── decisions/
│   ├── _INDEX.md             # 决策层：Git 跟踪
│   └── NNN-vN-keywords.md    # 决策层：Git 跟踪
└── .agents/                  # 个人层：Git 不跟踪
    └── <成员名>/
        ├── context.md        # 个人 AI 当前任务上下文
        └── scratchpad.md     # 草稿 / 探索期假设 / 待验证结论
```

| 层级 | 文件 | Git | AI 权限 | 内容 |
|---|---|---|---|---|
| 宪法层 | `AGENTS.md`、`BACKLOG.md` | 跟踪 | 起草-确认制 | 灵魂原则、红线、踩坑教训、排期 |
| 决策层 | `decisions/*.md` + `_INDEX.md` | 跟踪 | 起草-确认制；已确认决策不改写 | 已验证的团队决策 |
| 个人层 | `.agents/<成员名>/*.md` | 忽略 | 自由读写 | 当前任务上下文、探索期草稿 |

- **起草-确认制**：AI 可起草宪法层修改和新建决策文件，但不得单方面生效——多人模式下经人工 review 合并（PR 或同等确认流程）后才写入 main。人做闸门，不是人做誊写员。
- **个人层不是事实源**：`.agents/` 不进入 AGENTS.md 的文档职责表和 P1/P2 索引；其内容随时可弃。
- **scratchpad 与 temp_\* 的边界**：`scratchpad.md` 是跨会话持久草稿，不删除；`temp_*` 是用后即删的临时文件，两者互不混用。
- **成员标识**：`<成员名>` 用 git user.name；初始化时为当前成员建骨架，其他成员首次工作时由各自 AI 补建。

### 6.2 Git 策略

`.gitignore` 追加（已有文件增量合并，不覆盖）：

```gitignore
# 个人 AI 工作区
.agents/
```

初始化时创建 `.agents/<当前成员>/context.md` 与 `scratchpad.md` 骨架；`.gitignore` 条目保证个人层永不入库，成员间互不干扰。

### 6.3 晋升流程

```text
个人草稿（无序号、无版本号，随便改）
    ↓ 验证通过，成员决定晋升
AI 起草：读 main 最新 _INDEX.md 取 max+1 → 新建决策文件（此刻才有序号）
    ↓ 同 PR 内：_INDEX.md 追加索引行；教训类结论起草 AGENTS.md 踩坑教训章节修改
人工 review → 合并（= 确认生效）
```

- 草稿间互相引用写「见我的 XX 决策」，晋升落正式文件时才替换为 vN。
- 代码与决策文件同 PR 提交，commit message 引用决策文件名。
- 勤晋升是纪律不是机制要求：批量晋升永远可行，但攒多个决策挤一次 review 会降低 review 质量。

### 6.4 序号并发与撞号处理

| 环节 | 规则 |
|---|---|
| 认领 | 写决策文件时读 main 最新 `_INDEX.md` 取 max+1；序号 ↔ vN 一一对应 |
| 报警 | 并发晋升时决策文件（文件名不同）会静默合入，`_INDEX.md` 尾部追加必然冲突——冲突即报警，把同号并排摆到解决者眼前 |
| 修复 | 解决 `_INDEX.md` 冲突 = 看到重复序号 = 后合并者把自己的序号整体 +N（文件重命名 + 索引行改号 + 文内 vN 同步），纯机械操作 |
| 兜底 | 多人模式验收必查「`_INDEX.md` 序号无重复」，防两行追加位置恰好错开被 git 自动合并漏网 |

## 7. 踩坑教训章节规范

- 每条一句话：错误做法 → 正确做法。
- 使用 `L-NNN` 编号从 `L-001` 递增；条目仅追加，不重排、不改既有编号。
- 不预填未经项目实践验证的教训。
- 一句话式天然控制章节体积；不要求证据、规则、边界等多段结构。

## 8. Spec 层级约定

初始化时不主动创建 `specs/` 目录，只把层级约定写入 `AGENTS.md` 的 P1/P2 索引（一行说明）。Spec 在实际开发中按需创建，遵循：

- **目录树**：`specs/<模块>/<功能>/`，每个节点（根、模块、功能）一套三件套 `spec.md` + `tasks.md` + `checklist.md`。
- **按项目大小裁剪**：小项目只建根级三件套；中型项目展开模块级；大型项目全三层。模块和功能命名用小写英文连字符（如 `collector/session-search`）。
- **读取条件**：P1——任务命中某模块/功能时读取对应节点三件套，不整树预读。

```text
specs/
├── spec.md + tasks.md + checklist.md      ← 根级（项目总览）
└── <模块>/
    ├── spec.md + tasks.md + checklist.md  ← 模块级
    └── <功能>/
        └── spec.md + tasks.md + checklist.md  ← 功能级
```

## 9. 文档先行流程

1. 定位相关 Spec、决策和教训。
2. 读取现状，列出“文档现状 / 计划变化”。
3. 先更新文档并等待用户确认。
4. 严格按文档修改代码。
5. 运行用户已选择且实际安装的验证工具。
6. 回写 decisions/（新建决策文件 + `_INDEX.md` 追加索引行）、文档目录树和 AGENTS.md 踩坑教训章节。

## 10. 升级策略

已有文件时先读取，默认只补缺失段落。若旧文档含工具硬编码，而用户此次未选择该工具，应改成条件化说明，不得保留失效命令。

旧体系迁移：

- **`.trae/rules/soul.md` / `.trae/rules/lessons-learned.md` 存在**：soul 正文并入 `AGENTS.md` 的协作原则与红线章节，教训条目按第 7 节一句话格式并入踩坑教训章节；格式不符的旧条目压缩为一句话，不保留多段结构。展示“并入前 → 并入后”差异，确认无内容丢失后经用户明确授权删除两个旧文件；`.trae/rules/` 因此为空时可一并清理。
- **单文件 `决策日志.md` 存在**：按日期或条目逐条拆分为 `decisions/` 独立文件（命名 `序号-版本-关键词.md`），生成 `_INDEX.md` 索引表，经用户确认后删除旧文件。
- 迁移后不得残留指向已删文件的引用。
